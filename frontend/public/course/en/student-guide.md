# Student Quick Start

## 1. Start the System

From the project directory:

```bash
./start.sh start --mode auto
```

First startup may take longer to download images and dependencies. After startup:

- Frontend: `http://localhost:3000`
- Engine health: `http://localhost:8080/health`

Login credentials are generated by starter and saved in `docker/.env`. Import the
`CYANREX_ADMIN_TOTP_SECRET` into an authenticator as a Base32 secret, then log in with the 6-digit code.
Do not share this file or secret.

## 2. Understand the Interface

- **Dashboard**: view system status.
- **eBPF**: edit, check, run, and detach programs.
- **Environment Helper**: check kernel, BTF, bpftool, and mount points.
- **Events**: view kernel events and platform diagnostics.
- **Modules**: manage teaching modules and C headers.
- **Scripts**: script save area inside eBPF page.
- **Account**: change password and manage account.

## 3. Editor Capabilities

The editor is more than syntax highlighting:

- Runs real clang check ~700ms after typing pause.
- Red squiggle means errors, yellow means warnings.
- `ctx->` suggests real struct fields.
- `Ctrl/Cmd + click` jumps to definitions in the current file.
- Quick Fix can add common includes and GPL license.
- Outline shows hook, functions, and maps.

clang status:

- `checking`: in progress
- `passed`: syntax check passed
- `issues`: compile errors found
- `unavailable`: backend unavailable or account lacks permission

### Source Breakpoints

Click the editor gutter or press `F9` to toggle a breakpoint, then click **Compile and Run**.
Cyanrex implements eBPF breakpoints as non-blocking `bpf_printk` trace probes because a kernel eBPF
program cannot be safely paused like a userspace process. A red dot is requested, and a yellow dot
marks the latest hit received from the event stream.

The result panel lists instrumented lines and rejected positions. Comments, preprocessor directives,
global declarations, and unsafe multi-line expression positions are rejected. A maximum of 16 probes
is installed per run. The source must expose `bpf_printk`, normally through
`#include <bpf/bpf_helpers.h>`. If instrumentation itself fails to compile, Cyanrex retries the
original source and reports that the breakpoints were not installed.

Breakpoints are sampled trace events, not a correctness guarantee: a very hot line may execute more
often than the UI reports, and an unattached or untriggered program produces no hit.

## 4. A Complete Lab Run

1. Open Environment Helper and run check.
2. Select a template in eBPF page.
3. Read the code and predict output.
4. Wait for clang status to become `passed`.
5. Click **Compile and Run**.
6. Check compile/load/attach result stages separately.
7. Watch events in Events page.
8. Return to eBPF page and detach.
9. Ensure attached programs list is empty.

## 5. Lab Discipline

- Do not delete unknown bpffs files you cannot explain.
- Do not expose Engine ports to public network.
- Do not raise sample rate or event retention indefinitely.
- Do not run unknown eBPF programs.
- Always detach at the end of each lab.

The verifier blocks many illegal memory accesses, but it is not permission for running any arbitrary kernel code.
