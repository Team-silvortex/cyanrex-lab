## 学习记录流式提交增量（2026-09-08，收录于 0.3.5）

- 本地写入改由阻塞工作线程，以 64 KiB 缓冲流式输出逐字节兼容的 pretty JSON；显式 flush 后
  rename，再发布内存。不再分配完整编码文件缓冲，但仍重写整文件，快照及 SQL/HTTP/SDK 契约不变。
- 交接前取得写锁，每个 Store 最多一个排队/运行的提交；请求取消后工作线程仍持锁完成发布，
  修复磁盘/内存分歧与后续旧快照覆盖。交接前取消不启动写入，交接后可能保存成功但没有响应，
  重试前应先刷新；未新增追加幂等或崩溃/断电保证。
- 新增 9 项 Rust 回归，覆盖等待写锁/线程池排队、追加与评语 rename 后取消、脱离请求后的失败、
  流式输出、字节兼容、中断/部分写入及 flush 错误，完整安全门禁通过。
- 新的 72 轮磁盘配对矩阵以上一轮共享快照版本为基线，而非干净发行版。5 万条、源码 1,112 字节
  时，写入平均耗时 144.6 → 111.3 ms，p95 152.5 → 122.1 ms；1 万条的写入进程峰值 RSS 从
  63.2 降到 39.2 MiB。小规模写入平均值/p50 及部分未改动读取对照退化，大源码磁盘尾延迟波动明显，
  不能将本机结果解读为全面提速。
- 源码指纹和原始记录在 `reports/benchmarks/2026-09-08-learning-streaming-writes`，另有独立的
  72 轮 tmpfs 对照；取消、重试与关闭限制见[学习记录存储](learning-storage.md)。fsync、恢复日志、
  增量持久化及跨进程协调仍待推进。历史基准保留测量时的源码/版本指纹，不随 patch 升版重写，
  也不作为发行制品验收证据。

## LearningStore 快照与查询增量（2026-09-08，收录于 0.3.5）

- 本地读取共享不可变快照；最近审阅先有界筛选引用，再复制响应记录；学生进度和教师总览单次
  遍历聚合，不再克隆提交源码。追加只复制指针索引；评语额外复制被修改记录，旧读者快照不变。
- 新增 12 项 Rust 回归和 2 项基准排序回归，完整安全门禁通过。普通 pretty JSON、旧记录、SQL
  查询、授权、评语版本冲突和响应模式保持兼容，覆盖写入/重命名失败、并发更新与重载。
- 修正配对顺序后的 72 轮磁盘对比中，5 万条、源码 1,112 字节时，最近 20 条 p95 从 1.744 ms
  降到 0.220 ms，教师总览从 41.907 ms 降到 4.446 ms；写入进程峰值 RSS 从 296.3 MiB 降到

  对照虽有改善，但不能证明持久化磁盘性能；初版存在配对顺序缺陷的 72 轮数据单独保留，未合并或覆盖。
- 该测量阶段仍使用完整编码文件缓冲，rename/内存发布仍可被取消；上方后续增量替换了这两处机制，
  原始历史测量不重写。仍需整文件替换、常驻记录、指针索引复制和旧读者快照，未新增 fsync、恢复
  日志或跨进程协调。
- 行为和限制见[学习记录存储](learning-storage.md)，报告在
  `reports/benchmarks/2026-09-08-learning-snapshots-final`。

## 用户级事件分发增量（2026-09-08，收录于 0.3.5）

- `/ws/events` 按已认证会话用户建立有界实时队列，他人的突发流量不能挤掉本人排队事件；
  本人过载关闭、认证/来源检查和原始 JSON 保持兼容，旧 EventBus 全局服务订阅接口仍可用。
- 同一用户的连接共享不可变事件及惰性 JSON 编码；最后一个连接关闭/取消时清理队列，并处理
  并发重连时旧连接误删新队列的竞态。
- 新增 10 项回归，完整安全门禁通过。最终完成 30 轮 release 实验：24 轮当前分发路径对比、
  6 轮无订阅者二进制前后对照。在匹配输出一致时，单用户服务/数据帧构造吞吐提升约 24%–64%，
  8 用户提升约 40%–56%；另有 9 轮真实回环检查确认交付、显式过载和约 5 秒的慢连接清理。
  未缓存 JSON 的初版曾出现单用户退化，其结果保留而未被覆盖。
- 以上是本机合成基准，不代表局域网/内核或发行验收。容量按活跃用户计算，队列和 JSON 缓存
  内存随活跃用户及载荷增加；锁、持久化和 CPU 仍共享，尚未增加全局准入或持久化重放。
- 行为和复现命令见[事件流恢复](event-stream.md)，报告在
  `reports/benchmarks/2026-09-08-owner-fanout-final` 与 `2026-09-08-owner-event-stream`。

## 主动保留的边界

- 特权 Engine 面向可信自部署教学环境，不面向公网多租户。
- 本地执行共享同一个 Linux 内核；配额是资源控制，不等于学生隔离。
- Engine 仍是单进程。Agent 注册、远程作业、挂载和模块生命周期尚无多副本协调模型。
- Aya 当前覆盖已支持的 tracepoint 路径，bpftool 仍是兼容性最广的路径。
- 远程 Agent 只编译和诊断，`/ebpf/run` 仍在本地执行。

## 下一阶段决策点

1. 在把仅状态控制的模块目录扩展为进程或动态库插件前，先定义签名、真实隔离、可执行适配器与
   持久化所有权模型。
2. 在将 SDK 作为稳定、独立消费的软件包发布前，明确 Registry 发布、支持责任与 1.0 就绪标准。
3. 按桌面/局域网隔离目标补齐完整运行边界、持久化环境归属和 VM 恢复，再开启远程 eBPF 执行或
   Engine 多副本。
4. 在明确发布信任链与密钥归属后，对已验收候选产物签名并自动发布。
5. 收集首个注解 Tag 的真实内核验收证据，再决定是否需要在 GitHub 托管的特权 Docker 环境之外
   增加专用、自托管的多内核版本矩阵。

`engine/Cargo.toml` 是正式版本的唯一基准；`scripts/check-version-sync.sh` 会阻止前端、SDK、
OpenAPI 文档、锁文件和面向发布的文档再次漂移。
