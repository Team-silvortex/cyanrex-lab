# 事件历史按需读取优化与复测

## 结论

内存查询现在先在保留范围内选择匹配事件的引用，满足 limit 后停止，再只复制返回的数据。最新 200 条的读取成本不再随全部保留量增长；完整导出、时间/类别/等级筛选和 FIFO 返回顺序保持不变。

本轮对照的旧实现已经包含上一轮 `VecDeque` 发布优化，因此下面衡量的是读取优化的增量收益，不是与最初 Vec 发布实现的混合比较。

## 同口径查询延迟

release 库测试程序直接调用私有 `snapshot_for_user_filtered()`；每个场景 200 次查询，独立重复 3 次。以下为三次 p95 的中位数，单位 ms。

| 每用户保留条数 | 最新 200 条：优化前 | 最新 200 条：最终版 | 稀疏筛选：优化前 | 稀疏筛选：最终版 |
| --- | ---: | ---: | ---: | ---: |
| 500 | 0.139 | 0.051 | 0.158 | 0.006 |
| 5,000 | 1.641 | 0.045 | 1.689 | 0.067 |
| 20,000 | 9.009 | 0.037 | 9.747 | 0.050 |
| 50,000 | 24.859 | 0.037 | 24.264 | 0.051 |

稀疏筛选中约 5% 事件属于 kernel，查询最多返回 200 条；500 条历史只有 25 个匹配项，因此该行不是返回 200 条的成本。

最终版最新 200 条的 p95 区间：20,000 条容量为 0.0357–0.0378 ms，50,000 条容量为 0.0357–0.0376 ms。这是服务方法耗时，不是 HTTP 或页面渲染延迟。

没有匹配项时仍需检查保留范围，但不再克隆不匹配事件：20,000 条的 p95 从 5.588 降至 0.086 ms，50,000 条从 15.205 降至 0.186 ms。稀疏/无匹配查询仍可能扫描全部历史，不能概括为所有筛选均为 O(limit)。

## 分页读写混合压力

8 用户、32 个发布任务、8 个读任务，历史预填满；读任务每次请求最新 200 条，完成后睡眠 10 ms；发布阶段约 2 秒。没有订阅者或数据库。

| 历史容量 | 优化前发布吞吐（条/秒） | 最终版发布吞吐（条/秒） | 优化前发布 p95（ms） | 最终版发布 p95（ms） | 优化前读取 p95（ms） | 最终版读取 p95（ms） |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 500 | 544,115 | 610,673 | 0.074 | 0.071 | 0.801 | 0.422 |
| 20,000 | 1,282 | 592,600 | 41.818 | 0.073 | 60.309 | 0.384 |

20,000 条场景的最终版发布吞吐区间为 587,324–599,381 条/秒；全进程峰值 RSS 中位数由约 372.8 降至 206.9 MiB。RSS 包含预填、返回快照和统计缓冲，不等同于常驻 Engine 内存。

这是刻意放大的分页读取竞争，不是实际事件页的轮询方式。事件页在加载/筛选变化时读取历史，实时更新走 WebSocket；这里也不等同于上一轮“每次读取完整历史、固定发布条数”的压力模型。只能在本报告同一场景的前后版本之间计算收益。

## 完整导出的回退及修正

第一版按需选择实现直接逆序克隆 Event，再反转 Event 数组。分页变快，但完整导出明显变慢，因此没有采用该版本作为最终结果。

| 完整快照容量 | 优化前 p95（ms） | 中间方案 p95（ms） | 最终版 p95（ms） |
| --- | ---: | ---: | ---: |
| 5,000 | 0.813 | 1.578 | 0.756 |
| 20,000 | 3.818 | 8.177 | 3.801 |
| 50,000 | 9.147 | 19.916 | 9.451 |

最终实现先收集并反转轻量引用，然后按 FIFO 顺序克隆到已知大小的结果数组，避免逐步扩容 Event 数组及反转完整 Event。新增成本回归测试复现了中间方案“返回 200 条却扩容到 256 个 Event 槽位”，修正后通过。

最终版 50,000 条完整导出的 p95 区间为 9.204–10.872 ms，优化前为 9.016–9.635 ms；中位数约高 3.3%，在本轮共享主机测量中处于基线附近，但不据此承诺严格无回归。没有 CPU 采样来单独量化扩容、克隆顺序和反转的贡献。

完整导出仍要复制完整返回集，因此其成本依然随返回条数增长。共享历史读锁也仍然存在；本轮缩短了分页查询的持锁工作，并未实现按用户分锁或锁外快照。

## 实现和语义验证

- [引用选择器](../../../engine/src/services/event_bus_filter.rs)：按插入顺序从新到旧遍历，先裁剪 retention，再检查原有筛选条件、满足 limit 后停止；不假设事件时间戳有序。
- [内存查询入口](../../../engine/src/services/event_bus.rs)：数据库成功查询路径保持原样；内存路径只克隆选中的引用，并以原 FIFO 顺序返回独立的 `Vec<Event>`。
- 保留大小写/空白归一化、无效筛选值的现有行为、since_minutes、起止时间包含边界、空结果、零 limit、超大 limit、完整导出和用户隔离。
- 本轮新增 9 个正常回归测试，包括 2,160 组与旧 `filter_events` 的确定性结果对照、访问数量限制、时间戳乱序、结果分配上限及并发分页读取。
- 无筛选取 200 条只访问 200 条；limit=0 不访问历史；稀疏查询会继续扫描直到足够匹配，而不是扫描 limit 条就提前结束。选择器返回借用引用，深复制位于选择之后。
- TDD：引用选择器的 6 个新测试先失败再通过；随后为中间方案的结果扩容加入失败测试，再调整为引用收集/FIFO 克隆，最终 16 个事件相关正常测试全部通过。

## 环境、过程与限制

- 同一 Ryzen 7 7735H、Linux `7.0.0-30-generic`、Rust 1.95.0、16 Tokio worker；payload 字段 128 字节。
- 使用 release 构建的库测试可执行文件（含 `cfg(test)`），不是生产 Engine 二进制。手工 benchmark 默认 ignored，脚本只调用这一项，不需要公开服务接口。
- 18 个场景 × 3 次重复 × 3 个阶段，共 162 次有记录的运行；全部串行，轮换场景顺序，未与编译或其他门禁并行压测。
- 三阶段使用完全相同的 benchmark、运行脚本和场景参数，内容哈希已核对。此前有一次单场景确认用于检查导出修正，不计入这些矩阵统计。
- 优化前矩阵：2026-09-08 17:26:06–17:27:49；最终版矩阵：17:40:59–17:41:34，Asia/Shanghai。
- 优化前开始/结束 load average 分别为 1.53 / 1.66 / 2.22 和 2.57 / 2.07 / 2.31；最终版为 3.08 / 3.09 / 2.69 和 3.00 / 3.07 / 2.70。没有绑核、锁频或清空 OS 缓存。
- 计时包含服务方法生成返回 Vec 的工作，不含返回结果的释放、JSON 序列化或网络。旧实现丢弃未返回行的成本发生在方法内部，因此自然计入旧查询延迟。
- 快速场景只有 200 个样本/次，不应由这些结果建立 5% 级性能门槛。结果方向另由非计时访问/分配回归测试支持。
- 没有 PostgreSQL、真实 HTTP/WebSocket、浏览器或内核 eBPF 压测。本轮不证明上轮订阅 lag 已消失；慢消费者交付和用户级锁仍是后续工作。
