# 主线性能基线：2026-09-08

## 结论

本轮测到的首要扩展性瓶颈是 **EventBus 的满容量历史维护和历史复制**，其次是 **LearningStore 本地文件模式的全量处理**。编译检查/补全的缓存有效；突发请求遇到的是明确的并发保护，不能把 Busy 拒绝计入成功吞吐。

这是一次服务层基线与瓶颈诊断，不是生产容量承诺。没有修改业务实现、提高并发配额、连接真实数据库、加载 eBPF，也没有 commit/push。

## 环境与测量口径

- 业务源码：`0fc3f9b142eebcc5284876d1c8a3c3ecb0018dd8`，版本 0.3.3；新增 benchmark 的内容哈希另存于 metadata。
- 时间：2026-09-08 16:44:46–16:47:20，Asia/Shanghai。
- CPU：AMD Ryzen 7 7735H，8 核 / 16 逻辑线程；内存约 14.87 GiB；Linux `7.0.0-30-generic`。
- Rust `1.95.0`，Cargo release 优化构建，锁定依赖、离线构建；Node `18.19.1`；Tokio worker 固定为 16。
- Loader 优先选择的 `/usr/bin/clang` 为 Ubuntu Clang `18.1.3`，不是 PATH 中的 Android NDK Clang。
- 33 个场景，各 3 次，合计 99 次；串行运行，每轮轮换场景顺序，另有一次不计入结果的小规模预热。
- 表格取“各次运行指标的中位数”；区间为 3 次运行的最小值–最大值。p95 是每次运行按 nearest-rank 计算后再取中位数，不是合并全部请求的 p95。
- 发布吞吐包含事件构造和发布阶段调度；发布延迟只包围 `publish()`。预填历史、消费者收尾、统计排序不计入发布吞吐。
- GNU time 的 CPU、切换次数及峰值 RSS 覆盖整个进程，包括预填、清理和 Clang 子进程；RSS 不能解释为常驻 Engine 内存，也不是进程树同时存活内存之和。
- 测量在共享桌面主机进行，未绑定 CPU、锁频或清空页缓存；各场景开始时 1 分钟 load average 为 1.11–4.40（也包含 benchmark 自身负载）。快场景只有数百毫秒，不能据此设置 5% 级 CI 性能门槛。
- `perf_event_paranoid=4`；受限环境和批准后的外部重试均无法采集 perf 计数器。没有火焰图或函数级 CPU 占比，归因来自参数对照和源码证据，仍需优化后 A/B 复测确认。

## 1. EventBus：历史容量是最明显的性能拐点

共同条件：8 个用户，32 个发布任务，payload 字段 128 字节（不含事件信封），无订阅者和并发读取。每个用户历史在计时前已填满，使用 `DropOldest`，因此测的是持续淘汰旧事件的稳态。

| 每用户保留条数 | 发布吞吐（条/秒） | 吞吐区间（条/秒） | 发布 p95（ms） | 全进程峰值 RSS（MiB） |
| --- | ---: | ---: | ---: | ---: |
| 500（默认） | 365,244 | 352,574–378,177 | 0.125 | 14.1 |
| 5,000 | 94,970 | 91,868–96,961 | 0.413 | 57.1 |
| 20,000 | 7,321 | 6,282–7,489 | 5.761 | 200.0 |
| 50,000（允许上限） | 2,105 | 1,977–2,217 | 16.686 | 486.7 |

从默认 500 条提高到 20,000 条，吞吐降为约 **1/50**；提高到 50,000 条，降为约 **1/174**。这些是本次不同参数间的对比，不是版本回归。

并发本身没有带来扩展：相同默认容量下，1 个发布任务约 493,033 条/秒，32 个任务约 365,244 条/秒，后者低约 26%；p95 从 3.116 µs 增至 124.568 µs。这里的“任务”不是操作系统线程。

源码证据：

- [EventBus 历史结构](../../../engine/src/services/event_bus.rs#L29)是所有用户共享的 `RwLock<HashMap<String, Vec<Event>>>`。
- [发布路径](../../../engine/src/services/event_bus.rs#L120)每次获取历史写锁；满容量后 `Vec::drain` 移除头部，剩余元素需要前移。历史越长，每条发布的工作越多，且不同用户无法并行更新历史。
- 发布还涉及 settings/unread 全局锁及事件克隆。因此目前可以确认结构性放大，但不能给某一个锁或 `memmove` 分配精确 CPU 百分比。
- 配置数据库时发布也维护这份内存历史；数据库带来的额外开销本轮没有测量。

### 历史读取

单个用户、无并发写入，调用真实 `snapshot_for_user()`，每次取完整历史，共 100 次：

| 历史条数 | 完整快照 p95（ms） | 另行序列化最后 100 条 p95（ms） |
| --- | ---: | ---: |
| 500 | 0.099 | 0.053 |
| 5,000 | 0.974 | 0.067 |
| 20,000 | 3.991 | 0.056 |
| 50,000 | 9.998 | 0.066 |

[内存快照](../../../engine/src/services/event_bus.rs#L334)在持有共享读锁时克隆用户的整段历史；[带过滤的内存回退路径](../../../engine/src/services/event_bus.rs#L235)也是先复制，再过滤/裁剪 limit。即使 API 只要最新一页，复制成本仍随完整保留量增长。数据库成功查询路径不是这个实现，不能套用上述读取数值。

额外读写压力：8 个读任务各自“取完整快照，再睡眠 10 ms”。默认容量时发布约 280,094 条/秒；20,000 条时约 355 条/秒，发布 p95 114.7 ms、读取 p95 122.7 ms。该读延迟包含返回快照的释放成本。

**这不是当前页面流量模型。** [事件页](../../../frontend/pages/events.tsx#L21)默认请求 200 条，在页面加载/筛选变化时读取历史，实时更新走 WebSocket；[侧栏](../../../frontend/src/components/SidebarLayout.tsx#L138)每 4 秒轮询的是未读数，不是完整历史。10 ms 读任务只是锁竞争压力测试；“最后 100 条序列化”也不等于实际 200 条页面的端到端响应时间。

### 广播订阅

默认容量、8 用户、32 发布任务、60,000 条事件。订阅者模拟路由中的“接收全局广播 → 按用户过滤 → 对匹配事件做 JSON 序列化”，不建立真实 WebSocket：

| 订阅者数 | 发布吞吐（条/秒） | 发布 p95（ms） | 匹配投递 / 预期投递 | 广播 lagged |
| --- | ---: | ---: | ---: | ---: |
| 8（每用户 1 个） | 199,744 | 0.198 | 60,000 / 60,000 | 0 |
| 32（每用户 4 个） | 108,842 | 0.416 | 240,000 / 240,000 | 0 |

3 次重复均完整记账、没有 lagged。当前 [WebSocket 路由](../../../engine/src/routes/events.rs#L163)先从全局广播接收事件，再过滤用户，因此订阅者增加会增加无关事件的接收/克隆工作。数据支持将按用户分流列为后续方向，但不证明慢网络客户端不会丢消息；本轮也没有测浏览器逐事件渲染成本。

其余参数对照：1 用户约 471,732 条/秒，32 用户约 327,451 条/秒；payload 增至 4 KiB 后约 256,486 条/秒。完整数据见 summary。

## 2. 编译检查 / 补全：冷请求有成本，缓存有效

使用 `RunnerManager::local` 调用真实 Clang，但只用一个小型结构体访问 C 程序，不包含 vmlinux/BTF、大型头文件、eBPF 加载或 Agent 传输。默认非 resident 模式。

“冷”是更换尾部注释、强制应用缓存 miss，不是清空 OS 文件缓存；每次运行 50 请求。“热”在预填一个缓存项后重复 10,000 请求：

| 操作 | 冷请求 p95（ms） | 冷 p95 区间（ms） | 缓存命中 p95（µs） |
| --- | ---: | ---: | ---: |
| 语法检查 | 24.388 | 23.039–31.386 | 0.932 |
| 语义补全 | 22.443 | 22.184–24.486 | 1.122 |

冷场景全部成功且 0 命中；热场景全部成功且 100% 命中。微秒数只适用于服务内的小输入缓存路径，不是 HTTP/编辑器延迟。

每轮同时启动 32 个同源冷请求，共 20 轮，每次运行 640 个请求：

| 操作 | 成功 | Busy 拒绝 | 成功请求 p95（ms） |
| --- | ---: | ---: | ---: |
| 检查 | 40 | 600（93.75%） | 21.374 |
| 补全 | 60 | 580（90.625%） | 23.431 |

这与 [RunnerManager 的 2 / 3 个并发槽](../../../engine/src/services/runner_manager.rs#L116)及 [try_acquire 立即拒绝](../../../engine/src/services/runner_manager.rs#L249)一致。Busy 是容量保护，不是编译错误。下一步应测真实编辑节奏、去抖/重试体验和头文件场景；不应仅为了压低拒绝比例就提高配额。

## 3. 学习记录：本地文件模式存在全量放大

30 个合成学生，每条源码 1,112 字节；本地临时文件预加载完成后计时。recent 取一名学生最近 20 条、100 次；overview 聚合所有学生、10 次；record 每次新增一条失败编译记录、10 次，不执行学生代码。

| 初始记录数 | 最近 20 条 p95（ms） | 教师总览 p95（ms） | 新增记录 p95（ms） | 新增场景全进程峰值 RSS（MiB） |
| --- | ---: | ---: | ---: | ---: |
| 1,000 | 0.013 | 1.492 | 4.586 | 14.5 |
| 10,000 | 0.145 | 13.898 | 46.833 | 82.5 |
| 50,000 | 2.189 | 70.172 | 202.450 | 296.3 |

overview/record 每次只有 10 个延迟样本，nearest-rank p95 就是这 10 个样本的最大值；需要更长运行才能建立可靠尾延迟目标。

源码对应关系：

- [新增记录](../../../engine/src/services/learning_store.rs#L155)持有持久化互斥锁，克隆全部记录、追加、重写文件、替换内存集合。
- [文件持久化](../../../engine/src/services/learning_store.rs#L349)序列化整个集合为 pretty JSON，再写临时文件并 rename；50,000 条场景写入后文件约 73.95 MiB。没有 fsync，这不是断电耐久存储吞吐。
- [最近记录](../../../engine/src/services/learning_store.rs#L208)扫描全集，复制用户全部匹配项、排序后才裁剪至 limit。
- [教师总览](../../../engine/src/services/learning_store.rs#L228)取完整记录并重新分组、计算进度。

结论仅对本地文件模式成立。PostgreSQL 写入、SQL 查询计划、索引利用率和数据库总览聚合均未压测；不能拿这些数值代表数据库部署。

## 回到主线后的建议顺序

1. **先改事件历史数据结构。** 用有界环形队列/`VecDeque` 消除每条发布时的头部搬移，保留 DropOldest / DropNew 语义、排序和未读行为；分别对 500 / 5,000 / 20,000 / 50,000 容量复测。
2. **再改读取与锁粒度。** 在内存路径中先筛选/限制返回数量，再克隆需要的事件；评估按用户分离历史锁，确保清空、删除、设置变更及并发发布仍正确。保留跨用户隔离测试，不能用放松鉴权换吞吐。
3. **处理本地学习记录增长。** 优先避免最近记录/教师总览反复克隆全量源码；评估增量索引与追加型持久化。持久化格式变化属于单独设计，不在本轮直接替换。
4. **补真实端到端基线。** 局域网 HTTP + WebSocket、慢订阅者、浏览器渲染、独立测试 PostgreSQL，以及具备权限的 Linux eBPF 环境。按这些结果决定用户级广播和编译交互优化优先级。

后续优化重点应是现有 Rust 服务的数据结构和访问方式；收益以同口径复测为准。

## 重跑与原始记录

在仓库根目录执行，输出目录必须尚不存在：

```bash
node scripts/bench-mainline.mjs reports/benchmarks/mainline-local-confirmation 3
cargo test --manifest-path engine/Cargo.toml --release --locked --offline --example mainline_bench
```

脚本清除 `DATABASE_URL` 和 `CYANREX_BENCH_DATABASE_URL`，学习数据使用独立临时目录并在运行后清理。需要 Linux GNU time、Cargo 离线依赖缓存、Node 和支持相应检查的 Clang。

- [metadata.json](metadata.json)：完整参数、环境、业务 commit、benchmark/runner 内容哈希及完成状态。
- [runs.jsonl](runs.jsonl)：99 次运行的分布摘要、成功/拒绝/投递计数及进程资源数据；不是逐请求延迟列表。
- [summary.json](summary.json)：33 个场景各指标的中位数和最小/最大值。
- [Rust benchmark](../../../engine/examples/mainline_bench.rs)、[矩阵运行脚本](../../../scripts/bench-mainline.mjs)。

核验：release 构建、Rust 格式检查、脚本语法检查、文件行数检查通过；统计辅助函数 2 个测试通过；重复输出目录被拒绝且原报告未改变，benchmark 内容哈希与记录一致；99 次运行完整结束，事件接受数及订阅投递记账一致，编译成功数与 Busy 数之和等于尝试数。未运行完整产品质量门禁，因为本轮没有修改生产实现。

旧 `bench-event-bus` 从空历史开始，且通常使用 debug 构建、没有订阅者；本轮是 release + 满容量稳态。二者不能作为同口径前后性能对比，其内存回退验证也不能证明数据库已经完成持久化。
